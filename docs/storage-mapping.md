# 卡端访问主机磁盘的可行性

本文回答一个具体问题：能不能让卡上的 Linux 把主机上的一个文件、分区或
VHDX 当成块设备来用。结论按实现层级分开写，先说能做到哪一层，再说代价。

## 1. 现有的两条通路

主机和卡之间目前只有两条可用通路，别的都不成立：

- **启动通路。** 主机驱动把一整块镜像用 DMA 送进卡端内存，卡端固件从这块
  内存启动。镜像是只读的，启动完成后驱动不提供任何存储服务。
- **网络通路。** 主机侧 `nnpi-net-bridge` 把 TAP 设备和卡的以太网数据通道
  接起来，卡端地址 `192.168.115.2`，主机侧 `192.168.115.1`。这条通路已经
  跑过 iSCSI，实测 H2C 3.297 GB/s、C2H 3.482 GB/s。

所以“卡端读主机磁盘”不是有没有物理通路的问题，而是选哪一种块协议、以及
卡端内核里有没有对应的客户端。

## 2. L0：块级服务

卡端发起请求，主机应答，数据经 TAP 走现有的网络通道。这是唯一一条现在
就能落地的路线。

### 2.1 iSCSI

主机侧已经有一个能用的 iSCSI target，CrystalDiskMark 就是通过它跑的。
卡端如果带 `iscsi_tcp` 和 open-iscsi，直接 `iscsiadm` 登录即可，不需要写
任何新代码。

不确定的是卡端镜像。现有 rootfs 是 Buildroot 2019.11 定制的 initramfs，
默认配置通常不带 open-iscsi，也不一定编了 `iscsi_tcp`。先查：

```
zcat /proc/config.gz | grep -E 'ISCSI|NBD'
ls /lib/modules/$(uname -r)/kernel/drivers/block
which iscsiadm nbd-client
```

没有 `/proc/config.gz` 就查 `/boot/config-*` 或直接看 `/lib/modules`。

### 2.2 NBD

NBD 的协议比 iSCSI 小得多，握手只有几个固定结构，错误面也小。Linux 5.7
主线有 `nbd` 块设备驱动，Buildroot 里是一个独立选项，编进去的成本很低。

- 卡端：`nbd-client 192.168.115.1 10809 /dev/nbd0`
- 主机侧：需要一个 NBD server，把目标文件或 VHDX 作为后端。用户态实现
  几百行，读写直接用文件偏移，不需要动驱动。

如果卡端内核已经有 `nbd`，这是最短路径。没有的话，要么重建卡端镜像把
模块编进去，要么走 2.3。

### 2.3 自定义共享环

复用现有以太网数据通道的 DMA 描述符，把块请求直接压进同一对 H2C/C2H
队列。好处是不依赖卡端内核模块，坏处是主机侧要改 `nnpi-net-bridge` 或者
在用户态做多路复用，还要自己处理请求归属、完成顺序和错误恢复。

工作量比前两条大，但它也是后面做低延迟、零拷贝的基础。现在不建议先做。

### 2.4 性能预期

网络通道的 DMA 上限是 3.3/3.5 GB/s，块协议栈会吃掉一部分。参考主机侧
iSCSI 的成绩：顺序 4.6 GB/s 是四路 target 的总和，单路大约 1.2 GB/s；
4K 随机单线程约 7 万 IOPS。卡端是 4 线程 x86、约 500 MHz，单线程协议栈
会更慢，实际数字要实测。

### 2.5 边界

只暴露一个显式命名的文件、分区或 VHDX，不要给整盘。先只读跑通，再开写。
主机侧不要同时挂载同一个卷。

## 3. L1：钉页内存窗口

主机把一段物理页钉住，把 PFN 交给卡端，卡端在自己的页表里映射这段内存。

这条路单独做没有价值。卡端拿到窗口之后，读写仍然要经 PCIe，和块设备路径
搬的是同一批字节；省掉的只是一次拷贝。而“卡端直接 DMA 到主机内存”属于
L2，不是 L1 能解决的。

如果窗口只是主机把数据拷进卡端 RAM，那它就是一个拷贝缓存，和启动时把
镜像塞进去没有本质区别。

## 4. L2：卡端直接访问主机内存

需要卡端内核里有对应的 PCIe 端点驱动或地址窗口，还要有可用的地址翻译域。
当前镜像里没有这方面的证据，也没有公开的寄存器资料能支撑“猜一个地址试
一下”。猜错可能写到别的设备的 DMA 缓冲区，后果不可控。

在拿到明确证据之前，不把 L2 列进计划。

## 5. 推荐顺序

1. 探测卡端内核是否带 `nbd` 或 `iscsi_tcp`。这一步不改任何东西。
2. 有 `nbd` 就先做 NBD：主机侧最小 server + 一个 VHDX 或文件后端。
3. 有 `iscsi_tcp` 就直接用现成的 target。
4. 都没有，再决定是重建卡端镜像加模块，还是做共享环。
5. L2 只在拿到证据之后再谈。

现状（2026-10-22）：卡端 `nbd` 可用，第 2 步已经落地——16 GiB VHDX 通过
net-bridge 上的 TCP NBD 挂到卡端，协议、脚本和实测见
[storage-tcp-nbd.md](storage-tcp-nbd.md)。第 3 步的 iSCSI 仍只用于主机侧
跑分。

## 6. 和通用 Linux 启动实验的关系

通用 Linux 能启动之后，卡端 rootfs 由我们控制，`nbd`、`iscsi_tcp` 都可以
编进去，这条路会比在现有 initramfs 上想办法更直接。

但两件事不要绑死：卡端读主机磁盘不依赖通用 Linux。现有镜像如果已经带
`nbd`，今天就能做。先探测，再决定要不要重建。

## 7. 驱动侧的最小改动面

启动上传路径把镜像当成一段不透明的字节流：181 个 1 MiB chunk 加最后一个
512 字节，共 188,744,192 字节。协议只传描述表和总长度，不解析分区表，也
不关心 ESP 里放的是哪个内核。

硬编码只有一处：`include/nnpi_image_identity.h` 里的
`NNPI_APPROVED_IMAGE_BYTES` 和 SHA-256。0.3.0.20 只接受
`936f4888...d4841b5` 这一个镜像。所以换镜像的第一步不是改 DMA：

1. 新镜像补齐到 188,744,192 字节。ESP 只占前 180 MiB，尾部补零不影响
   引导；SHA 在 seal 时对 chunk 的实际字节计算，补零要作为镜像的一部分。
2. 更新 allowlist 的尺寸和摘要。
3. 重新编译、签名、安装。签名和安装按现有约束单独授权，不在本文范围内。

如果新镜像大于 188,744,192 字节，就必须改尺寸常量；chunk 数会跟着变，
守护逻辑不用动。

## 8. 观测手段

卡端没有物理串口，现有镜像靠 Xvfb + x11vnc 看画面。通用镜像如果要在启动
阶段排错，console 必须落到一个拿得到的地方，否则只能看到“卡住了”。

这一步要在做镜像之前定下来，不要等启动失败之后再找。
